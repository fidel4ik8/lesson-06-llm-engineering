Technical sync — Архітектурне рішення для нового search service
Дата: 24 квітня 2026
Учасники: Сергій (Tech Lead), Юлія (Senior Backend), Артем (DevOps), Богдан (Backend)

Сергій: Привіт всім. Сьогодні фіналізуємо архітектуру нового search-сервісу. У нас є три опції: Elasticsearch, Meilisearch, або self-hosted на PostgreSQL з pg_trgm. Юля, ти готувала benchmark?

Юлія: Так. Коротко: на нашому обсязі — це близько 12 мільйонів документів — Elasticsearch виграє по швидкості повнотекстового пошуку, ~40ms p95. Meilisearch — 70ms, але набагато простіший в підтримці. PostgreSQL — 200ms+, не підходить.

Артем: З точки зору інфри — Elasticsearch це JVM, потребує мінімум 16GB RAM на ноду, плюс кластер з трьох нод для HA. Meilisearch — один бінарник на Rust, 2GB RAM достатньо. Різниця в інфраструктурних витратах приблизно $800/місяць.

Сергій: Богдан, ти працював з обома. Думки?

Богдан: Elasticsearch потужніший, особливо для агрегацій та фасетного пошуку. Якщо ми плануємо аналітику в майбутньому — це плюс. Meilisearch — швидко стартуєш, але якщо знадобиться щось складне, упремося в стелю.

Юлія: Питання — чи реально нам потрібні агрегації? З продуктового боку зараз вимога — швидкий fuzzy search по назвах товарів і фільтри по 4-5 полях.

Сергій: Окей, рішення: беремо Meilisearch. Простіше, дешевше, покриває поточні потреби. Якщо за рік виростемо в потребах — зробимо міграцію. Записую.

Артем: Я підготую Terraform-модуль для деплою Meilisearch у нашому Kubernetes. До 8 травня буде готово, з моніторингом через Prometheus.

Юлія: Я візьму імплементацію search-сервісу. Це Go-мікросервіс, який буде проксі між API і Meilisearch, з кешуванням популярних запитів у Redis. Дедлайн — 22 травня.

Богдан: Я займусь індексацією. Треба написати worker, який слухає Kafka events про зміни товарів і оновлює індекс. Плюс bulk reindex job для початкового завантаження. До 18 травня.

Сергій: Добре. Ще пара рішень. По-перше — всі нові сервіси пишемо на Go, Python тільки для ML. По-друге — обов'язково OpenTelemetry tracing з першого дня. По-третє — індекс конфіг тримаємо в Git, не змінюємо руками в проді.

Артем: Згода по всіх трьох. Ще пропоную: rate limiting на рівні API gateway, не в самому search-сервісі. Так буде чистіше.

Сергій: Приймається. Юля, додай у свій список — інтегрувати з нашим існуючим rate limiter.

Юлія: Записала.
